# PostgreSQL database

The database of the backend, for a local PostgreSQL in Docker and for Supabase. The same `.sql` files build both, and the API picks one with `DATABASE_PROVIDER` in `services/api/.env`. The data model is the one in [mvp_architecture.md](../../docs/mvp_architecture.md), section 2, moved from SQLite to PostgreSQL and split into three schemas.

## Folders

```
database/postgresql/
  schema/      CREATE statements. Run in name order. Edit by hand
  seeds/       INSERT statements. Generated by services/api/seed.py. Do not edit by hand
  scripts/
    apply.sh            Runs schema/ and then seeds/ against an empty database
  docker-compose.yml    Local PostgreSQL that runs apply.sh on its first start
  .env.example          Copy to .env (not in git)
```

## Schemas

Every table lives in one of three schemas, by what kind of data it holds. Table names carry no prefix: `cfg.rule`, not `cfg.cfg_rule`.

| Schema | Holds | Changes |
| :-- | :-- | :-- |
| `cfg` | Configuration: sources, indicators, rules | When the team adds an indicator or a rule |
| `dat` | Data: the crew and their readings | Every day |
| `his` | History: append-only records of sync operations and audit. Empty for now | Only grows |

In Supabase only the `public` schema is exposed through the Data API by default. These three are not, so the tables are reachable only through the FastAPI backend.

## Tables

### `cfg.source`

Where an indicator's data comes from (R11).

| Column | Type | Notes |
| :-- | :-- | :-- |
| `id` | `TEXT` PK | Readable key, e.g. `lifesnaps` |
| `name` | `TEXT` | |
| `url` | `TEXT` | |
| `citation` | `TEXT` | How to cite it in the app and in the submission |

### `cfg.indicator`

One thing we measure (R4, R8). A new indicator is a new row, not a new column.

| Column | Type | Notes |
| :-- | :-- | :-- |
| `id` | `TEXT` PK | Readable key, e.g. `glucose` |
| `name` | `TEXT` | |
| `unit` | `TEXT` NULL | `NULL` for the mood indicators |
| `how_to_measure` | `TEXT` | The brief asks for it per measurement |
| `why_it_matters` | `TEXT` | The short explanation for R4 |
| `source_id` | `TEXT` FK → `cfg.source` | |
| `display_order` | `INTEGER` UNIQUE | Order of the panel. New: SQLite used `rowid`, PostgreSQL has none |

### `cfg.rule`

A limit on an indicator, with its explanation, what to do and where the limit comes from (R10, R11).

| Column | Type | Notes |
| :-- | :-- | :-- |
| `id` | `INTEGER` PK, identity | Same ids as in SQLite, so the contracts do not change |
| `indicator_id` | `TEXT` FK → `cfg.indicator` | |
| `low`, `high` | `DOUBLE PRECISION` NULL | At least one is set. A value exactly on a limit does not break the rule |
| `title`, `explanation`, `action` | `TEXT` | |
| `threshold_source` | `TEXT` | Never a limit without it |

### `dat.crew_member`

A fictional astronaut.

| Column | Type | Notes |
| :-- | :-- | :-- |
| `id` | `INTEGER` PK, identity | |
| `name` | `TEXT` UNIQUE | |

### `dat.reading`

One value of one indicator for one crew member at one moment.

| Column | Type | Notes |
| :-- | :-- | :-- |
| `crew_member_id` | `INTEGER` FK → `dat.crew_member` | |
| `indicator_id` | `TEXT` FK → `cfg.indicator` | |
| `taken_at` | `TIMESTAMP` | No time zone, as in the MVP architecture. Daily values and blood draws at 00:00 |
| `value` | `DOUBLE PRECISION` | Moods are 1 or 0 |

Primary key `(crew_member_id, indicator_id, taken_at)`. It also serves the two queries of the API.

There is still no alert table: a reading is an alert when it breaks a rule of its indicator, and the API computes it.

## Change the data

- **A text, an indicator or a rule:** edit `services/api/seed_content.py`, then regenerate the seeds.
- **The crew or how a dataset becomes readings:** edit `services/api/seed.py`, then regenerate the seeds.
- **A table or a column:** edit `schema/`, the SQLAlchemy models in `services/api/app/models.py`, this README and the MVP architecture in the same commit.

Regenerate the seeds and commit them:

```sh
cd services/api
uv run python seed.py
```

## Run it locally

Needs Docker.

```sh
cd database/postgresql
cp .env.example .env          # then set POSTGRES_PASSWORD
docker compose up -d          # first start: creates the schemas and loads the seeds
docker compose down -v        # deletes the data; the next `up` rebuilds it from the .sql files
```

## Choose the database of the API

In `services/api/.env` (copy it from `.env.example`):

| `DATABASE_PROVIDER` | Uses | Connection |
| :-- | :-- | :-- |
| `postgresql` | `POSTGRESQL_URL` | The local Docker database. No SSL |
| `supabase` | `SUPABASE_DATABASE_URL` | SSL required. On the transaction pooler (port 6543) prepared statements are turned off |

Both go through SQLAlchemy with psycopg 3 and the same models. The differences live only in `services/api/app/db.py`.

## Load it into Supabase

Into an empty project, with `psql` and the connection string from Project Settings → Database. Never commit it.

```sh
DATABASE_URL="postgresql://..." sh database/postgresql/scripts/apply.sh
```
