# PostgreSQL database

The database of the backend, for a local PostgreSQL (installed, or in Docker) and for Supabase. The same `.sql` files build both, and the API picks one with `DATABASE_PROVIDER` in `services/api/.env`. The data model is the one in [mvp_architecture.md](../../docs/mvp_architecture.md), section 2, moved from SQLite to PostgreSQL and split into three schemas.

## Folders

```
database/postgresql/
  schema/      CREATE statements. Run in name order. Edit by hand
    00_schemas.sql      The cfg, dat and his schemas
    01_cfg.sql          Sources, indicators, rules
    02_dat.sql          Crew and readings
    03_sync.sql         sync_seq on the synchronised tables, and the sync history
    04_auth.sql         Users, sessions and sign-in events
    05_daily_tasks.sql  The daily checklist and the ticks of each crew member
  seeds/       INSERT statements. Generated by services/api/seed.py. Do not edit by hand
  scripts/
    apply.sh            Runs schema/ and then seeds/ with psql. Used by docker-compose
  docker-compose.yml    Optional local PostgreSQL that runs apply.sh on its first start
  .env.example          Copy to .env (not in git)
```

## Schemas

Every table lives in one of three schemas, by what kind of data it holds. Table names carry no prefix: `cfg.rule`, not `cfg.cfg_rule`.

| Schema | Holds | Changes |
| :-- | :-- | :-- |
| `cfg` | Configuration: sources, indicators, rules | When the team adds an indicator or a rule |
| `dat` | Data: the crew and their readings | Every day |
| `his` | History: append-only records. For now, the moon-earth synchronisations (`his.sync_operation`) | Only grows |

In Supabase only the `public` schema is exposed through the Data API by default. These three are not, so the tables are reachable only through the FastAPI backend.

## Tables

### `cfg.source`

Where an indicator's data comes from (R11).

| Column | Type | Notes |
| :-- | :-- | :-- |
| `id` | `TEXT` PK | Readable key, e.g. `lifesnaps` |
| `name` | `TEXT` | |
| `url` | `TEXT` | |
| `citation` | `TEXT` | How to cite it in the app and in the submission |

### `cfg.indicator`

One thing we measure (R4, R8). A new indicator is a new row, not a new column.

| Column | Type | Notes |
| :-- | :-- | :-- |
| `id` | `TEXT` PK | Readable key, e.g. `glucose` |
| `name` | `TEXT` | |
| `unit` | `TEXT` NULL | `NULL` for the mood indicators |
| `how_to_measure` | `TEXT` | The brief asks for it per measurement |
| `why_it_matters` | `TEXT` | The short explanation for R4 |
| `source_id` | `TEXT` FK → `cfg.source` | |
| `measured_by` | `TEXT` | `sensor`, `astronaut` or `computed`: who takes the measurement |
| `cadence_days` | `INTEGER` NULL | A new reading is expected every this many days. `NULL` when computed |
| `display_order` | `INTEGER` UNIQUE | Order of the panel. New: SQLite used `rowid`, PostgreSQL has none |

### `cfg.rule`

A limit on an indicator, with its explanation, what to do and where the limit comes from (R10, R11).

| Column | Type | Notes |
| :-- | :-- | :-- |
| `id` | `INTEGER` PK, identity | Same ids as in SQLite, so the contracts do not change |
| `indicator_id` | `TEXT` FK → `cfg.indicator` | |
| `low`, `high` | `DOUBLE PRECISION` NULL | At least one is set. A value exactly on a limit does not break the rule |
| `title`, `explanation`, `action` | `TEXT` | |
| `threshold_source` | `TEXT` | Never a limit without it |

### `dat.crew_member`

A fictional astronaut.

| Column | Type | Notes |
| :-- | :-- | :-- |
| `id` | `INTEGER` PK, identity | |
| `name` | `TEXT` UNIQUE | |
| `role` | `TEXT` | `commander` or `crew_member` |

### `dat.reading`

One value of one indicator for one crew member at one moment.

| Column | Type | Notes |
| :-- | :-- | :-- |
| `crew_member_id` | `INTEGER` FK → `dat.crew_member` | |
| `indicator_id` | `TEXT` FK → `cfg.indicator` | |
| `taken_at` | `TIMESTAMP` | No time zone, as in the MVP architecture. Daily values and blood draws at 00:00 |
| `value` | `DOUBLE PRECISION` | Moods are 1 or 0 |

Primary key `(crew_member_id, indicator_id, taken_at)`. It also serves the two queries of the API.

There is still no alert table: a reading is an alert when it breaks a rule of its indicator, and the API computes it.

### `sync_seq`, on every synchronised table

`schema/03_sync.sql` adds a `sync_seq BIGINT` column to `cfg.source`, `cfg.indicator`, `cfg.rule`, `dat.crew_member` and `dat.reading`. It takes the next number of the sequence `his.sync_seq` on every insert, and a trigger (`his.bump_sync_seq`) gives it a new one on every update. A synchronisation sends the rows above the last `sync_seq` already sent. The SQLAlchemy models leave it out on purpose: the database fills it in, and only `services/api/app/sync.py` reads it. How the moon and earth servers use it is in [moon_earth_sync.md](../../docs/moon_earth_sync.md).

### `his.sync_operation`

One row per synchronisation between the moon and earth servers, successful or not. Append only.

| Column | Type | Notes |
| :-- | :-- | :-- |
| `id` | `BIGINT` PK, identity | |
| `direction` | `TEXT` | Moon: `push` or `pull`. Earth: `received_push` or `served_pull` |
| `peer` | `TEXT` | The other server |
| `started_at`, `finished_at` | `TIMESTAMPTZ` | |
| `status` | `TEXT` | `ok` or `failed` |
| `row_count` | `INTEGER` | Rows sent, received or applied |
| `from_seq`, `to_seq` | `BIGINT` NULL | The `sync_seq` range included. The next sync in that direction starts at `to_seq`. Empty when it failed |
| `error` | `TEXT` NULL | Why it failed. Never medical data |

## Change the data

- **A text, an indicator or a rule:** edit `services/api/seed_content.py`, then regenerate the seeds.
- **The crew or how a dataset becomes readings:** edit `services/api/seed.py`, then regenerate the seeds.
- **A table or a column:** edit `schema/`, the SQLAlchemy models in `services/api/app/models.py`, this README and the MVP architecture in the same commit.

Regenerate the seeds and commit them:

```sh
cd services/api
uv run python seed.py
```

## Choose the database of the API

In `services/api/.env` (copy it from `.env.example`):

| `DATABASE_PROVIDER` | Uses | Connection |
| :-- | :-- | :-- |
| `postgresql` | `POSTGRESQL_URL` | A local PostgreSQL, installed or in Docker. No SSL |
| `supabase` | `SUPABASE_DATABASE_URL` | SSL required. On the transaction pooler (port 6543) prepared statements are turned off |

Both go through SQLAlchemy with psycopg 3 and the same models. The differences live only in `services/api/app/db.py`.

For Supabase, copy the **Session pooler** connection string (Connect, or Project Settings > Database). The direct connection only works over IPv6, which many networks lack.

## Load the data

`load_database.py` creates the tables and loads the seeds into the database that `DATABASE_PROVIDER` points to. It needs neither psql nor Docker, and works the same for both databases.

```sh
cd services/api
uv run python load_database.py             # creates what is missing; never touches existing data
uv run python load_database.py --rebuild   # deletes cfg, dat and his with all their data and loads again
```

| It finds | It does |
| :-- | :-- |
| None of the schemas | Creates the tables and loads the data |
| The tables, empty | Loads the data |
| The tables, with data | Nothing. Use `--rebuild` |
| Only some of the schemas | Stops and asks you to check, or to use `--rebuild` |

Everything runs in one transaction: if any statement fails, the database is left as it was. The database itself must exist: a new Supabase project already has one (`postgres`), and on a local server create it once with `CREATE DATABASE real_telemetry;`.

After regenerating the seeds, or changing a table, run it with `--rebuild`.

### With Docker instead

```sh
cd database/postgresql
cp .env.example .env          # then set POSTGRES_PASSWORD
docker compose up -d          # first start: creates the schemas and loads the seeds
docker compose down -v        # deletes the data; the next `up` rebuilds it from the .sql files
```
